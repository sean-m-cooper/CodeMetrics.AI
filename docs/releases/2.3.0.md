# CodeMetrics.AI 2.3.0

This release improves source measurement and contextual findings, and makes missing
dependency evidence an explicit assessment failure. It targets .NET 10, emits schema
3, and uses ruleset `dotnet-2026-09-14-dependency-availability`.

## Scoring and measurement

- Complexity & Decomposition exposes separate method-complexity and decomposition
  components. Methods, accessors, local functions and callbacks own their decisions;
  nested bodies do not inflate their enclosing function's CC. Method complexity
  counts each authored source function once across project/framework observations.
- Method complexity combines 40% of the worst function's score with 60% of the
  remaining mean. CC anchors 3/5/10/20/40 map to 10/8/6/4/0 with linear interpolation.
- Maintainability measures executable functions, counts authored functions once,
  and excludes enums and non-executable declarations. It combines 40% of the weakest
  fifth's mean with 60% of the remaining mean. The two groups do not overlap.
- Aggregate rounding uses decimal arithmetic with midpoint ties up. Partial classes
  aggregate as logical types; raw CSV measurements remain separate from scoring.

## Context and scope

- Solution build configuration exclusions and production/test/support roles are
  respected. Repeated framework observations do not multiply source-site findings.
- Security distinguishes descriptive identifiers from credential candidates and
  recognizes bounded CORS rejection guards.
- Error handling recognizes local rationale and exception-bearing handling patterns,
  scoring the severity-weighted source catch population. Documented deliberate
  swallowing is not automatically treated as an empty catch defect.
- Async checks distinguish actionable waits from proven completion and narrowly
  established synchronous contracts. Recognized contextual cases remain unscored
  review leads, not declarations of runtime safety. Unknown callbacks, mixed callers
  and unsupported dispatch remain conservative.
- The packaged CMAI catalog explains rule identifiers, evidence and supported local
  rationale annotations. Existing codes retain their identities.

## Dependency failures

A restore or package-command failure cannot restore a clean score from partial
output. Missing candidate compatibility metadata now withholds Dependency
Management's score instead of creating upgrade penalties. Unknown observations
have informational severity and `scoreDisposition: unavailable`.

Evidence records grouped failure reasons, unique package/version counts, affected
project/TFM observations, known observations and elapsed time. Failed discovery,
HTTP responses, package size limits, shared-budget exhaustion, unavailable versions
and unsupported frameworks can be distinguished where observed. The existing
bounded timeouts remain; this release does not introduce retry or persistent caches.

Confirmed vulnerabilities/deprecations survive independently failed checks. An
unavailable vulnerability query also withholds Security's score while preserving
static findings. A compatibility-only failure does not erase a successful
vulnerability query. Failed dimensions have no score or scoring decision; the CLI
and inspector return 2, and no overall score should be calculated.

## Adoption

Install the NuGet tool with `dotnet tool update --global CodeMetrics.AI --version 2.3.0`
(use `install` for a first installation). The coordinated `ai_tools` code-scorecard
skill update pins this version, exposes assessment failure details and distinguishes
missing evidence from code defects. Update that skill through its normal repository
or plugin distribution mechanism; installing the analyzer alone does not refresh it.

The evidence inspector remains `codemetrics-ai` npm version 0.3.0. No new npm package
is required for this .NET release; its existing schema-3 contract supports the new
failure details.

Generate fresh baselines. Changes to populations, formulas, classification and
availability can change scores without source changes; earlier rulesets are not
compatible baseline gates. A successful run remains a partial static assessment,
not proof of coverage, runtime performance or the absence of vulnerabilities.

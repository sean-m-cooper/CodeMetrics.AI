# CodeMetrics.AI architecture

CodeMetrics.AI is a deterministic, read-only analyzer. It loads a .NET solution or explicit project with Roslyn, collects production metrics, runs nine independent scorecard probes, and writes CSV metrics plus schema-v3 JSON evidence.

## Analysis flow

1. `Program.cs` parses command-line options and passes cancellation to the analysis pipeline.
2. `SolutionScope` reads solution build mappings with SolutionPersistence. `Program` loads the solution or project with the selected MSBuild configuration (Any CPU). Project mode scores only the selected project while keeping references in the workspace for semantic resolution. `SolutionCompilationLoader` classifies enabled projects, bounds concurrent compilations to four, and records missing compilations and compiler errors. Disabled projects remain explicit filter entries and are excluded from both source compilation diagnostics and package checks; enabled production compilation errors remain blocking.
3. `MetricsCollector` groups included production declarations by Roslyn type symbol within each project/framework compilation. Partial declarations contribute to one logical type: member aggregates are calculated once, partial member definitions/implementations count once, and raw/structural coupling uses the union of dependencies. Generated/excluded declarations are not imported through symbol references. Source-line counts retain physical declaration overhead. A deterministic representative file and the full included source-file list retain provenance; component hotspot samples expose the logical identity and files.
4. Each class in `Probes/` evaluates one scorecard dimension. Probes receive immutable metric or compilation inputs and return a `DimensionResult`.
5. `CsvWriter` and `EvidenceWriter` persist the two public output formats.

The dependency probe is the only probe that invokes external commands or reads package feeds. Those operations are bounded, cancellable, and degrade to explicit failed or unknown evidence rather than silently inventing compatibility.

Dependency subprocesses remove the MSBuild paths installed by the analyzer's locator and resolve their own SDK from the repository working directory. When a solution excludes projects from its build, package commands receive a disposable solution containing only enabled projects. Static dependency checks use the same selected paths. Source architecture cycles use production paths, and testing aggregates a union of unique source sites across target frameworks. Test/support/sample exclusions do not remove enabled package dependencies from the dependency assessment.

## Important boundaries

- `Metrics/` owns Roslyn metric calculation. Raw Roslyn-compatible class coupling remains available even when architecture scoring uses structural coupling.
- `Probes/` owns findings and score ladders. A probe should report observable evidence; it should not mutate the analyzed solution.
- `Output/` owns serialization only. Evidence shape changes must remain compatible with `shared/scorecard-schema/evidence.schema.v3.json`.
- `Rules/rules.json` owns permanent CMAI aliases, descriptions and annotation capabilities. The package embeds the catalog and ships JSON/Markdown copies. `code-metrics rules` serves the installed version without loading a solution. Findings retain their existing rule IDs and fingerprints while exposing codes in observations; dimensions reference metric-only entries separately. New rules must be cataloged and assigned unused codes; do not renumber or reuse existing codes. Regenerate `Rules/rules.md` with the CLI after editing the catalog. Consumers must check package version and catalog version before presenting annotation guidance.
- Tests exercise probes with in-memory Roslyn compilations where possible. End-to-end tests are reserved for solution loading, command execution, and output contracts.

## Design invariants

- C&D scoring uses `executable-function-ownership-v1`, independently of the unchanged raw CSV metrics. Each method, named local function, callback, implemented accessor and expression-bodied property/indexer owns its decisions; nested function bodies are measured separately. Branching field/property initializers are measured too. Method complexity uses distinct authored functions under `source-function-own-cc-v1`; the earlier executable-functions-v2 policy used type maxima. Decomposition uses `(1 + sum(qualifying own CC)) / qualifying function count`, requiring at least two qualifying functions. Storage members and bodyless declarations do not qualify; branch-free callbacks/initializers do not add denominator units. Named local functions count like private methods. Trivial named-helper extraction can still improve this proxy without improving design. Types retain their project/framework identity; raw coupling, maintainability, CSV member counts and aggregate complexity are unchanged. Explicit legacy `TypeMetrics` inputs without executable measurements retain their old inputs and are disclosed by `legacyInputTypes`; production collection always supplies executable measurements.
- The earlier C&D policy IDs end in `executable-functions-v2`; ruleset `dotnet-2026-09-11-executable-functions` separated those measurements from earlier baseline gates. Hotspots expose scoring `maxMemberCc`, `decompositionRatio`, `decompositionComplexity`, `decompositionFunctionCount` and sampled `functions` with own CC and locations. `rawMaxMemberCc`, `rawDecompositionRatio`, `classCc` and `memberCount` retain raw measurements. Decomposition retains those threshold bands. The later method-population policy below replaces only the method-complexity component.

- Scores must be deterministic for the same source, configuration, analyzer version, and package-source responses.
- Ruleset `dotnet-2026-09-12-method-population` and C&D policy `dotnet/codeQuality/method-population-v3` apply the accepted 40/60 method-complexity formula. Each function receives a linearly interpolated score at own CC 3/5/10/20/40 → 10/8/6/4/0, clamped to 0–10. Forty percent of one worst function plus sixty percent of the remaining mean forms the aggregate; a single-function scope uses its individual score. Decimal arithmetic precedes one half-up aggregate rounding. Empty populations remain unmeasured despite a policy default.
- Method complexity groups physical source path, function name/defining-token offset and function kind across projects/TFMs, taking the maximum observed own CC per authored function. Conditional declarations at different starts and callbacks on the same line stay distinct. Hotspots retain variant observations and source spans. Missing source identities are counted separately and disclosed. Decomposition is still measured per type instance; root executable-function totals are observations, not the new complexity denominator. Explicit legacy/mixed input lacking complete function metrics retains the former type-maximum complexity policy and is labeled `legacy-type-maxima-v1`.
- Maintainability uses a separate `MaintainabilityFunctions` population with `source-function-own-mi-v1`: owned body tokens, source lines and CC exclude nested function bodies. Runtime initializers count even without branching; compile-time constants and empty lambda wrappers do not. Enums and declarations supply no credit. Repeated physical file/defining-token/kind observations use the lowest own MI once, with missing identities left separate and missing measurements failed. Explicit legacy/mixed type metadata retains a labeled legacy policy.
- Ruleset `dotnet-2026-09-12-function-maintainability` activates `dotnet/maintainability/source-functions-quintile-40-60-v1`: linear MI anchors 40/52/58/65/70/75 → 0/2/4/6/8/10, then 40% weakest-fifth mean plus 60% remaining mean. Function groups are disjoint, distribution statistics are diagnostics only, and there is no entry-point bonus. One function uses its own score; zero is unmeasured. Decimal scoring rounds once with midpoint ties up. Raw type/member MI and CSV remain unchanged; new scores cannot be compared with former policy baselines.
- The existing `deductions` evidence operation represents the weighted formula as shortfalls from 10, with explicit weights, worst individual score, remaining mean, population counts, unrounded result and aggregate ceiling. This preserves schema-v3 validation. Consumers must not treat those deduction steps as individual-method scores or apply the new weights to earlier policies.
- Ruleset `dotnet-2026-09-12-score-rounding` retains executable-function ownership and adds decimal score averaging/rounding with midpoint ties away from zero (.5 up for nonnegative scores). Decisions record the rounding mode, arithmetic and precision. C&D and maintainability use `linear-decimal-v1` percentile interpolation before comparing full measurements against unchanged bands; display rounding must not select a threshold. Raw metrics and CSV rounding retain their existing behavior.
- Error-handling penalties count distinct rule/severity/source-span findings, not repeated project/framework observations. Shared authored files count once; different files, source spans and rules remain distinct. Each finding retains affected project/framework labels and original messages. Missing file identity is conservatively left unmerged. Method complexity has its own distinct-source-function population; decomposition and other type-metric populations and package observations retain their existing policies.
- Error handling recognizes exception-bearing returns and invoked error delegates alongside logging/rethrow. Roslyn must resolve the caught exception symbol and the invoked factory/constructor/delegate; a reassigned catch variable does not qualify. Returned factories, constructors, object initializers and tuples can carry the exception, including returned factory wrappers. An outcome stored by a direct catch statement and returned through a local or an operation returning that same outcome type also qualifies when no intervening assignment or ref/out use is found. Void delegates and awaited delegate invocations receiving that exception are handling paths and do not require an ILogger member. Discarded results, unrelated exceptions and deferred lambda/local-function bodies within the catch are not evidence of handling. Existing recognition of captured exceptions logged by callbacks registered after the catch is preserved. These are bounded static observations, not proof that a result factory retains the exception or that an optional callback runs on every path. Exception aliases, custom reporting methods and interprocedural mutations remain review cases.
- Splitting a type into partial files must preserve its member complexity, decomposition, maintainability and coupling measurements. Physical source-line counts can still change with declaration headers and formatting. Same-named nested/generic types and different project/framework instances remain separate; CSV membership uses logical identity, not a short-name join.
- Direct synchronous `System.Console.Error.Write` / `WriteLine` calls with arguments are recognized reporting paths for broad and multiple-catch checks. Roslyn resolves the `Console.Error` property and `TextWriter` method, including qualified, aliased and static-import forms. Deferred bodies, parameterless blank writes, arbitrary writers and lookalike Console types do not establish stderr reporting. This is a bounded recognition rule, not validation of message quality or reporting on every path; writer aliases and asynchronous reporting remain review cases. Evidence records `stderrReportingRecognition: system-console-error-v1` separately from exception propagation.
- Generated code, build output, and test projects never enter production type metrics.
- A missing or failed signal is reported as skipped, failed, or unknown; it is never treated as a clean result.
- Suppressions are category-specific and require a nearby reason.
- Concurrency recommendations must account for ordering, back-pressure, shared contexts, and framework thread-safety.
- Package upgrade scoring uses the candidate package's target-framework assets, not version-major guesses.

## Verification

ExecutableFunctionCollector traverses each included type declaration once, measuring function identity and own CC once for both scoring populations. Complexity and Maintainability retain separate initializer eligibility: a branching compile-time constant can remain a C&D observation while a branch-free runtime initializer belongs only to Maintainability. C&D evidence omits the MI payload; shared collection must preserve source anchors, ordering and both population definitions.

From the repository root:

```powershell
dotnet restore analyzers/dotnet/CodeMetrics.AI.slnx
dotnet test --solution analyzers/dotnet/CodeMetrics.AI.slnx --configuration Release --no-restore
dotnet build analyzers/dotnet/CodeMetrics.AI.slnx -c Debug --no-restore /p:Version=1.3.3
dotnet analyzers/dotnet/src/CodeMetrics.AI/bin/Debug/net10.0/CodeMetrics.AI.dll --solution analyzers/dotnet/CodeMetrics.AI.slnx
```

The final command refreshes `.scorecard/dotnet/metrics.csv` and `.scorecard/dotnet/evidence.json` beneath `analyzers/dotnet`.

EvidenceEnricher coordinates catalog metadata, source attribution, finding identities, confidence and scoring explanations. FindingSourceResolver owns syntax/member lookup and repository-relative source paths. Fingerprints retain the original identity fields, source anchors, target-framework distinction and per-dimension occurrence ordering; refactoring this path must not make unchanged findings appear new. Incomplete source analysis retains findings but removes source-derived scores and returns exit code 2.

CoverageReport owns file reading, hashing, guarded XML parsing and invalid-report handling. CoverageSourceAccumulator owns matching Cobertura classes to production files and merging line hits, including repeated observations. Aggregate branch rates remain unknown when unrelated files prevent attribution to the matched subset. Parsing and attribution can evolve independently without changing the report contract.

CompletedTaskAccess keeps Boolean completion-proof composition separate from direct Task-property checks and helper-body verification. For an AND guard, either conjunct can establish completion; for an OR guard, both alternatives must establish it. Helpers must prove the state of the same receiver through a single returned expression, without calls or receiver writes. Names alone never establish completion, and guards outside a deferred body do not establish its execution-time state.

ConcurrentFanOutProbe separates source-tree traversal, captured-argument detection and finding construction. Each recognized fan-out site reports its first demonstrated captured-state mutation. Parameter aliases are computed once per authored method for the current analysis and reused while mutation summaries reach a fixed point; they are not cached across runs. This avoids repeated syntax scans without changing mutation propagation or broadening the probe's deliberately bounded recognition.

TargetFrameworkParser normalizes supported framework names into ParsedFramework values. TargetFrameworkCompatibility owns compatibility decisions, including platform restrictions and unknown results when unsupported asset names prevent a definite answer. Parsing syntax and compatibility policy have separate change boundaries; moving them does not expand the supported frameworks or infer compatibility from an unrecognized name.

`WorkspaceDiagnostics` records the exact MSBuild design-time load in temporary binary logs because Roslyn 5.9 flattens MSBuild warning/error severity in workspace callbacks. Only callbacks matched to recorded warning events (and no matching error) become nonblocking `workspaceWarning` diagnostics. Explicit errors and unknown failures remain blocking. Logs are replayed with cancellation and removed after analysis; the evidence schema and CSV columns are unchanged.
